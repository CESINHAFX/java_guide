## 1. Contexto e Perfil do Aluno  
- **Descrição do Perfil:**  
  - **Background:** Alunos que estão se iniciando ou já possuem conhecimentos básicos de programação e desejam compreender como a engenharia de software se apoia em ferramentas e fluxos de trabalho modernos (especialmente Git e GitHub) para colaboração e versionamento.  
  - **Nível:** Pode ser aplicado tanto para Iniciantes (com pouca ou nenhuma experiência com Git) quanto para Intermediários que precisam estruturar melhor o fluxo colaborativo em projetos reais.  
- **Objetivos de Aprendizagem para Engenharia de Software com Ênfase em Git:**  
  - **Primário:** Compreender e praticar os principais comandos, fluxos (clonagem, branching, commits e merges) e estratégias de colaboração com Git e GitHub.  
  - **Secundário:** Entender papéis e responsabilidades (desenvolvedor, integrador, administrador) e aplicar boas práticas que evitam conflitos e promovem a integração contínua.  
- **Stakeholders:** Aluno | Mentor | Comunidade  
- **Critérios de Sucesso:**  
  1. Explicar e aplicar fluxos de trabalho com Git em cenários reais.  
  2. Executar exercícios práticos com criação de branches, pull requests e resolução de conflitos.  
  3. Adaptar o fluxo conforme feedback e dificuldades encontradas.  

> **Mini-Resumo / Checklist:**  
> – Perfil direcionado a iniciantes e intermediários.  
> – Objetivos claros de utilização prática de Git na colaboração em projetos.  
> – Ênfase na aplicação e feedback contínuo.

## 2. Conceitos e Variáveis-Chave  
- **Conceitos Fundamentais de Engenharia de Software (com foco em Git):**  
  1. **Git Workflow:** Fluxo de trabalho envolvendo clonagem, criação de branches, staging, commit, push, pull request e merge.  
  2. **Clonagem vs. Fork:** Entender quando criar uma cópia local de um repositório (clone) e quando derivar um novo projeto a partir do original (fork).  
- **Variáveis Imutáveis / Boas Práticas:**  
  - Mensagens de commit claras e descritivas.  
  - Isolamento de funcionalidades em branches separadas.  
  - Revisão de código por meio de pull requests.  
- **Representação Gráfica:**  
  - Sugestão de fluxograma demonstrando o ciclo: Repositório Remoto → Clone → Branch → Commit → Push → Pull Request → Merge.  
- **Tabela Resumida:**

  | Conceito       | Descrição                                           | Exemplo/Observação                              |
  | -------------- | --------------------------------------------------- | ----------------------------------------------- |
  | Clone          | Copiar o repositório remoto para máquina local      | `git clone https://github.com/exemplo/projeto.git` |
  | Branch         | Espaço isolado para desenvolvimento de uma feature  | `git branch feature-nova` e `git checkout feature-nova` |
  | Commit         | Registro das mudanças realizadas                     | `git commit -m "Implementa recomendação de produto"`  |
  | Pull Request   | Solicitação para integrar alterações à branch principal | Revisão e merge pelo mantenedor                 |

> **Mini-Resumo / Checklist:**  
> – Conceitos centrais de versionamento e colaboração.  
> – Importância dos comandos e boas práticas destacadas.

## 3. Cenários Práticos e Análise de Riscos  
- **Cenário A (Fácil):**  
  - **Descrição:** Projeto com um único desenvolvedor utilizando Git para versionar e documentar alterações simples.  
  - **Exemplo:** Criação e commit de um arquivo HTML utilizando `git init`, `git add` e `git commit`.  
- **Cenário B (Médio):**  
  - **Descrição:** Projeto colaborativo onde vários desenvolvedores criam branches, realizam commits e submetem pull requests para revisão.  
  - **Exemplo:** Implementação de uma nova funcionalidade (ex.: recomendação de produtos) e integração via pull request.  
- **Cenário C (Difícil):**  
  - **Descrição:** Projeto com múltiplos integrantes, conflitos frequentes de merge e requisitos de integração contínua (CI/CD).  
  - **Exemplo:** Merge de diversas branches com revisão rigorosa e resolução de conflitos complexos.  
- **Desafio Extra:**  
  - Implementar um workflow envolvendo fork de um repositório open-source, contribuição via pull request e sincronização com o upstream.  
- **Riscos / Pontos Críticos:**  
  - Conflitos de código decorrentes de alterações simultâneas.  
  - Falhas na comunicação entre as equipes sobre os status dos branches.  
  - Estratégias: Utilizar diagramas de fluxo, exercícios de simulação de merge e uso de ferramentas visuais.

> **Mini-Resumo / Checklist:**  
> – Três cenários escalonados em complexidade.  
> – Desafios extras para ampliar o aprendizado.  
> – Identificação e mitigação de riscos importantes.

## 5. Perguntas de Verificação (Cenários A/B/C)  
1. **Pergunta 1:** Explique como o workflow Git ajuda a evitar conflitos em um projeto colaborativo.  
   - **Cenário A (Fácil):** Descreva o uso básico do commit para versionar alterações.  
   - **Cenário B (Médio):** Explique a importância de branches isoladas e pull requests para revisão.  
   - **Cenário C (Difícil):** Descreva estratégias avançadas (como rebase ou cherry-pick) para resolver conflitos persistentes.  
   - **Desafio Extra:** Discorra sobre como sincronizar um fork com o repositório upstream.  
2. **Pergunta 2:** Qual a diferença entre clonar e forkar um repositório?  
   - **Cenário A (Fácil):** Responder que clonar cria uma cópia local, enquanto forkar cria um repositório derivado na conta do usuário.  
   - **Cenário B (Médio):** Concordar os contextos de uso – colaboração interna versus contribuição open-source.  
   - **Cenário C (Difícil):** Discutir implicações em termos de permissões e sincronização de alterações.  
3. **Pergunta 3:** Como você resolveria um conflito de merge em uma situação onde dois desenvolvedores alteraram a mesma linha de código?  
   - Explique a identificação do conflito (usando `git status` e `git diff`), a resolução manual e a finalização com commit.

> **Mini-Resumo / Checklist:**  
> – Perguntas escalonadas com complexidade variável.  
> – Abordagens e soluções modeladas para cada nível.
